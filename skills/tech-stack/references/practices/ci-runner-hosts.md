# Runner hosts: tuning long-lived self-hosted runners

Extends the Runners section of [CI](ci.md). Measure first (see [CI options](ci-options.md)); a small host is harmed by advice written for large fleets.

- Before pruning build cache, check when each entry was last used (`docker buildx du --verbose`). "Reclaimable" in `docker system df` counts every entry no running container holds, including cache used minutes ago; pruning hot cache only slows the next builds. Prune with `--filter until=<age>`, and treat a prune that frees nothing as a sign that the cache is in use, not as a reason to drop the filter.
- Run every runner on a host as one service user. A runner per user copies the setup actions' tool cache, mise and rustup toolchains, package stores and a rootless Docker per user, and that duplication can outweigh everything the host's cleanup can free.
- On a long-lived self-hosted runner, install toolchains once on the host through mise, pinned by the project's `mise.toml`, rather than using `setup-*` actions in every job. Keep one pnpm store on the same filesystem as the runners' work folders so installs hardlink, and skip `actions/cache` there: on one disk it only adds an upload and a download.
- Route by job length with labels: one light runner for jobs under about a minute (change detection, aggregate gates, packaging) and the others for heavy jobs. On a small runner fleet, quick checks otherwise queue behind long test jobs. Fold tiny jobs into neighbours where the gate rules allow it, since each job pays runner start-up, checkout and install.
- Use `fetch-depth: 1` except in jobs that need history (versioning, releases, base-ref diffs), and sparse checkout for jobs that read a few paths. A job that needs history but only names (`merge-base`, `diff --name-only`, `log`) can add `filter: blob:none`. Never add it where the job reads old file contents (`git show`, content diffs, history secret scans) under `persist-credentials: false`: in a private repo, git fetches those blobs on demand with no credentials and the job fails.
- Do not run more concurrent jobs than the host's memory allows: on a 2-core, 4 GB host that is already swapping, more runners slow every job.
